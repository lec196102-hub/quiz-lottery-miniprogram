## 1. 一句话结论

> **没有任何一个开源项目能直接满足本需求。** 答题类项目普遍缺少"奖品池 + 概率控制 + 库存扣减"，抽奖类项目则完全没有答题与身份登记能力。
>
> **推荐路径**：以微信云开发方案自建（借鉴 WeZhi 的题库导入与后台架构 + lucky-canvas 的抽奖动画），而非二次改造现有答题项目。理由见 §6。

### 3.3 关键结论

**答题类全部缺失的三件事**（恰恰是本需求的核心）：

1. **奖品池与概率控制** —— 无一具备"恒定 25% 中奖率 + 库存扣减"模型。
2. **身份登记（姓名 + 工号）** —— 大多依赖微信 openid 自动登录，无法做线下核销身份绑定。
3. **一人一次抽奖的强约束** —— 答题项目是"可重复练习"，与"抽奖唯一性"天然冲突，改造成本高于重写。

**抽奖类全部缺失的三件事**：答题能力、服务端概率托管、中奖名单后台。且 lucky-draw、lucky-canvas 均为**纯前端**组件，概率逻辑在客户端 → **可被篡改，不可用于真实发奖**。

## 4. 架构对比

### 4.1 四种典型架构

| 架构模式 | 代表项目 | 结构 | 适用 |
| --- | --- | --- | --- |
| **A. 纯前端 / 单机** | lucky-draw、landluck/lucky_wheel | 数据在浏览器内存或 localStorage | 现场年会大屏，无实名、无持久化 |
| **B. 小程序 + BaaS（云开发）** | WeZhi、Wapp、hydrogen-lottery | 小程序 ⇄ 云函数 ⇄ 云数据库 | **轻量活动，快速上线** |
| **C. 小程序 + 自建服务** | QuestionWechatApp(PHP)、dati(SpringBoot)、lotteryMiniprogram(Django) | 小程序 ⇄ HTTP API ⇄ MySQL ⇄ Web 后台 | 长期平台、数据自主 |
| **D. 组件库（无业务）** | lucky-canvas | 只提供抽奖 UI 与动画 | 作为任何架构的表现层嵌入 |

### 4.2 重点架构解析：WeZhi（最贴近本需求）

```
cloudfunctions/mcloud/              ← 单云函数承载全部后端（路由分发）
├── framework/                       ← 自研 MVC 框架
│   ├── core/application.js          应用入口
│   ├── platform/controller|service|model/   分层基类（含 base_admin_* 鉴权基类）
│   ├── database/{db_util,model,multi_model}.js   数据访问封装
│   ├── utils/{export_util,data_util,time_util}.js
│   └── validate/{data_check,content_check}.js    导入校验 + 内容安全
├── project/cbexam/                  ← 业务模块（题库/考试）
│   ├── controller/admin/*           后台接口（home/mgr/news/question/user/setup）
│   ├── service/admin/*
│   ├── model/{question,answer,user,news,fav}_model.js
│   └── public/route.js              路由表
└── index.js

miniprogram/
├── cmpts/public/{form,list,rows,calendar,editor,file}/   ← 高度组件化的动态表单/列表
├── helper/{cloud_helper,page_helper}.js
└── projects/cbexam/
```

**架构评价**

- ✅ **单云函数 + 内部路由**：避免云函数数量爆炸，冷启动可控，是云开发下的务实选择。
- ✅ **后台管理"配置化"**：动态表单 + 通用列表组件，新增一个管理页几乎零代码，这套思路值得直接借鉴。
- ✅ **导入链路完整**：`data_check`（校验）→ `data_util`（转换）→ `setup_util`（初始化），并配套 `export_util`。
- ⚠️ **缺点**：单云函数会让代码体积膨胀（框架 + 业务耦合）；MVC 分层对本项目（8 个接口）属于过度设计。

### 4.3 重点架构解析：kesixin/dati（自建服务代表）

```
小程序端（uni-app）  ─┐
PC/H5（Vue）         ─┼─▶ SpringBoot / PHP API ─▶ MySQL ─▶ Vue 管理后台
```

- ✅ 多端覆盖（小程序 + H5 + PC），适合长期产品化。
- ⚠️ **商业性质明显**：README 大量篇幅引导加微信/QQ 获取完整源码与部署文档，开源仓库中的前后端完整源码可用性与时效性存疑。
- ⚠️ 需域名备案 + HTTPS + 服务器，一次性活动成本高。

### 4.4 重点架构解析：lucky-canvas（抽奖表现层）

```
@lucky-canvas/mini   微信小程序
@lucky-canvas/uni    uni-app
@lucky-canvas/vue    Vue2/3
@lucky-canvas/react  React
@lucky-canvas/taro   Taro 3.x
lucky-canvas         原生 JS / JQ
```

- ✅ **跨平台抽奖插件事实标准**，提供大转盘 / 九宫格 / 老虎机三种形态，官方文档完善（100px.net）。
- ✅ 支持"前端指定中奖结果"：`prizeIndex` 由服务端返回后驱动动画，可与服务端概率逻辑完美解耦。
- ❌ **仅负责 UI 与动画**，不含任何概率、库存、名单能力。

**技术栈趋势判断**

1. **云开发已成答题类小项目主流**（WeZhi、Wapp、Kuai-Shua 均采用）—— 免备案免运维，契合"一次性活动"。
2. **PHP 老项目仍在维护但技术债明显**（QuestionWechatApp 限定 PHP ≤ 7.2，已 EOL）。
3. **uni-app 是长期产品化的选择**（dati），代价是多端适配成本与构建复杂度。

### 6.2 为什么不直接二次开发

| 判断依据 | 说明 |
| --- | --- |
| 核心能力缺口是**服务端**的 | 需求 R5–R8（概率、库存扣减、唯一性、名单）全部在服务端，而答题类项目的服务端要么没有（纯前端），要么只服务答题业务，改造等于重写 |
| 改造成本 > 自建成本 | 本需求接口仅 10 个左右、页面 5 个，自建约 8 人日；读懂并改造一个 2 万行自研框架的云开发项目至少需要同等时间，且背负他人技术债 |
| 抽奖是**资金/实物风险**场景 | 概率必须服务端控制、库存必须原子扣减、名单必须可审计——借用不成熟的开源抽奖逻辑（如 37★ 项目）风险不可控 |
| 授权风险 | Star 最高的几个答题项目均声明"禁止转发/盗卖"，二次开发与分发存在法律隐患 |

### 6.3 最终选型建议

```
┌─────────────────────────────────────────────────────────┐
│  架构借鉴  WeZhi  —— 云开发 + 单云函数路由 + 配置化后台思路  │
│  表现层    微信原生小程序 + Vant Weapp                      │
│  抽奖 UI   lucky-canvas（@lucky-canvas/mini）              │
│  核心自研  报名模块 · 答题引擎 · 抽奖引擎 · 奖品池 · 名单后台  │
│  题库导入  借鉴 WeZhi 的 data_check + export_util 校验链路   │
└─────────────────────────────────────────────────────────┘
```

| 层次 | 结论 |
| --- | --- |
| 架构模式 | **云开发（方案 A）**，一次性活动首选；长期平台才考虑 uni-app + SpringBoot |
| 抽奖 UI | 直接引入 **lucky-canvas**，不自研动画 |
| 题库导入 | 直接借鉴 **WeZhi** 的校验 + 导入 + 导出链路设计 |
| 抽奖引擎 | **100% 自研**（这是本项目的唯一技术壁垒，也是必须做对的部分） |
| 明确排除 | QuestionWechatApp / dati（PHP 老旧 + 授权风险）、lucky-draw（纯前端不可控）、37★ 级抽奖小程序（质量无保障） |
