## 1. 项目概述

### 1.1 背景

企业内部知识答题活动（如安全生产月、制度宣贯、党建知识竞赛）需要一个轻量、可快速上线、能现场发放奖品的互动工具。核心诉求是：**扫码即用、答题通关、抽奖发奖、后台可查**。

### 1.2 产品定位

一款**微信小程序**形态的**答题 + 抽奖**一体化活动工具，形态为：

> 扫码 / 点链接进入 → 登记姓名工号 → 随机抽 5 题作答 → 答对 3 题通关 → 抽奖 → 中奖结果即时展示 → 后台可查获奖名单

### 1.3 目标与非目标

**目标（本期必须）**
1. 支持 150 道单选题的批量导入与维护。
2. 支持参与者扫码/链接入场，登记姓名 + 工号。
3. 每次从题库随机抽取 5 题，答对 ≥3 题即通关并获得抽奖资格。
4. 抽奖：一等奖 5 份、二等奖 50 份、三等奖 100 份，总中奖概率恒定 25%，中奖后实时扣减奖池库存。
5. 同一工号 + 姓名仅可抽奖一次。
6. 管理后台可查看获奖名单（姓名、工号、奖项、中奖时间）并导出。

**非目标（本期不做）**
- 实物奖品邮寄 / 物流跟踪、奖品核销二维码。
- 排行榜、积分体系、错题本、题库分类（后期可选扩展，见 §10）。
- 多活动并行（本期按单活动设计，但数据模型预留 `activity_id`）。

### 1.4 关键指标（供验收参考）

| 指标 | 目标值 |
| --- | --- |
| 首屏加载（4G，冷启动） | ≤ 2.5 s |
| 抽题接口响应 | P95 ≤ 400 ms |
| 抽奖接口响应 | P95 ≤ 600 ms |
| 抽奖并发 | 支持 200 QPS 无超发、无重复中奖 |
| 数据正确性 | 奖品发放总数 = 155，零超发、零重复 |

| --- | --- | --- |
| **参与者（员工）** | 扫码参加答题抽奖 | 快速参与、少填信息、结果即时可见、公平 |

```

      │
      ▼
[登记页：姓名 + 工号]  ──校验工号格式/重复──▶ 已存在 → 直接复用身份
      │
      ▼

      │
      ▼

             ▼

        ┌────┴────┐

        │           │
        ▼           ▼
  [几等奖 + 动画]  [谢谢参与]
        │
        ▼
   [我的奖品 / 兑奖凭证]
```

| 项 | 说明 |

### 3.2 R2 身份登记

| 项 | 说明 |
| --- | --- |
| 字段 | 姓名（必填，2–10 字）、工号（必填，按企业规则校验） |
| 校验规则 | 姓名：中文/英文，去首尾空格；工号：数字或字母数字组合，长度 4–12，正则可后台配置 |
| 身份唯一性 | 唯一键：`(activityId, empNo, name)` |
| 重复登记 | 已存在 → 不报错，静默复用原身份记录，进入其答题/抽奖状态（避免员工换手机重复抽奖） |
| 数据存储 | 同时记录 `openid`（用于同设备识别，但**不作为唯一性依据**） |
| 隐私 | 姓名工号仅用于本次活动核销，活动结束后可后台一键脱敏导出 |

### 3.3 R3 题库管理（150 道单选）

| 项 | 说明 |
| --- | --- |
| 题型 | 单选题（4 选项 A/B/C/D） |
| 批量导入 | 后台上传 Excel/CSV，模板列：`题号,题干,选项A,选项B,选项C,选项D,正确答案,解析(选填)` |
| 导入校验 | 必填项非空、正确答案必须在 A–D 内、题干去重（按题干哈希）、选项不得重复 |
| 导入结果 | 返回"成功 N 条 / 失败 M 条"，失败行可下载错误报告 |
| 覆盖策略 | 三种可选：① 全量覆盖；② 增量追加；③ 跳过重复（默认②） |
| 单题维护 | 后台支持增删改查、启用/停用（停用题不参与抽题） |
| 容量 | 150 题（设计容量 5000 题，无性能压力） |

**导入模板示例**

| 题号 | 题干 | 选项A | 选项B | 选项C | 选项D | 正确答案 | 解析 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 灭火器的有效期一般是？ | 1年 | 3年 | 5年 | 10年 | C | 依据 GB 50444 |

### 3.4 R4 答题与通关

| 项 | 说明 |
| --- | --- |
| 抽题 | 服务端从**启用状态**的题库中随机抽 5 题（不放回） |
| 抽题接口 | 仅返回 `题干 + 4 个选项 + 题号`，**不下发正确答案** |
| 作答交互 | 单题单页（推荐，仪式感强）或列表式；可跳题、可修改，交卷前可回看 |
| 判分 | 客户端提交答案数组 → 服务端比对 → 返回得分与是否通关 |
| 通关条件 | 5 题中答对 ≥ 3 题（**阈值后台可配置**） |
| 重答规则 | 未通关可无限次重新抽题作答；已通关仍可继续答题（练习），但不再发放抽奖资格 |
| 答题结果页 | 展示答对题数、通关状态、正确答案与解析（可配置是否展示解析） |
| 防作弊 | 不设倒计时（内部学习性质），但服务端记录每次作答明细备查 |

### 3.5 R5/R6 抽奖引擎（核心）

#### 3.5.1 奖品配置

| 奖项 | 数量 | 初始占比 |
| --- | --- | --- |
| 一等奖 | 5 | 3.2% |
| 二等奖 | 50 | 32.3% |
| 三等奖 | 100 | 64.5% |
| **合计** | **155** | 100% |

参数（后台可配置）：总中奖概率 `P = 25%`、各奖项数量、各奖项权重、活动开关。

#### 3.5.2 抽奖算法（重点）

**两阶段模型**——先判"中不中"，再判"中几等"，保证总中奖率恒为 25%。

```
阶段一：中奖判定
  r1 = crypto-random 浮点 [0, 1)
  if r1 >= P(0.25) → 未中奖，返回"谢谢参与"，结束
  ↓ 中奖（25%）

阶段二：等级分配（在"仍有库存"的奖项中按权重抽取）
  candidates = 所有 remain > 0 的奖项
  if candidates 为空 → 降级为"谢谢参与"（奖池已空）
  按权重加权随机选中一个等级 L
  ↓

阶段三：原子扣减库存
  UPDATE prize SET remain = remain - 1
  WHERE activity_id=? AND level=L AND remain > 0
  ├─ 影响行数 = 1 → 扣减成功，发放 L 等奖
  └─ 影响行数 = 0 → 并发下被抢完，从 candidates 移除 L，回到阶段二（最多重试 3 次）
                     仍失败 → 降级为"谢谢参与"，记录 lottery_fallback 日志
```

**等级权重策略（需决策，见 §11-Q1）**

- **方案 A｜按剩余库存加权（推荐）**：权重 = 当前剩余数量。库存越少越难中，一等奖自然稀缺，全程平滑，无需人工干预。
  - 首次抽奖中一等奖的概率 ≈ 25% × (5/155) ≈ 0.81%
- **方案 B｜固定权重**：一/二/三等奖权重固定为 1 : 8 : 16（可配置）。等级分布更可控，一等奖发放节奏可预期；某级抽完即剔除并重归一。
- **方案 C｜按初始库存比例**：权重固定为 5 : 50 : 100。实现最简单，但一等奖会在前 1/3 参与者中快速抽完，后期"中奖但只有三等奖"。

> 实现建议：权重策略做成配置项（`WEIGHT_MODE = remain | fixed | initial`），默认 A，后台可切换。

#### 3.5.3 奖池扣减与耗尽

- 中奖即扣减，`remain` 字段原子自减，绝不超发。
- 某等级 `remain = 0` 后自动从候选中剔除，后续参与者不可能抽到该等级（**对应需求"5 个一等奖被抽走后不再抽到一等奖"**）。
- 总中奖概率 **始终维持 25%**，不因奖池变少而升高或降低（**对应需求"中奖概率保持不变"**）。
- **奖池全部抽空后**：抽奖入口展示"奖品已全部送出，感谢参与"。可选配置为"仍允许点击但必定谢谢参与"（默认采用前者，体验更明确）。

#### 3.5.4 规模测算（重要）

按 25% 中奖率、155 份奖品：

| 参与抽奖人次 | 期望已送出奖品 | 剩余奖品 |
| --- | --- | --- |
| 155 | ~39 | ~116 |
| 310 | ~78 | ~77 |
| **620** | **~155（抽完）** | **~0** |
| 800 | 155（已空） | 0 |

> **结论**：需要约 **620 人次**完成抽奖才能把 155 份奖品送完。若参与人数远低于 620（例如仅 200 人通关），活动结束时奖品会有大量剩余，需提前规划（追加轮次 / 提高中奖率 / 缩小奖池）。此测算应写入活动筹备清单。

### 3.6 R7 抽奖资格与唯一性

| 项 | 说明 |
| --- | --- |
| 状态机 | `未登记 → 已登记 → 已通关(passed) → 已抽奖(drawn)` |
| 答题次数 | 不限 |
| 抽奖次数 | 每人 1 次（唯一键 `(activityId, empNo, name)`） |
| 重复通关提示 | 已抽奖用户再次通关后点击抽奖 → 提示「每人仅可参与一次抽奖」，并展示其历史中奖结果 |
| 防绕过 | 抽奖接口服务端强校验；数据库唯一索引兜底；同一 openid 5 秒内重复请求直接返回上次结果（幂等） |

### 3.7 R8 管理后台

| 模块 | 功能 |

### 4.2 抽奖引擎执行时序（并发安全关键路径）

```
Client                Service                    DB
  │  POST /lottery/draw   │                       │
  ├──────────────────────▶│                       │
  │                       │ 1. 校验登录态+资格     │
  │                       │ 2. 唯一索引插入        │
  │                       │    lottery_record ────▶│ (失败=已抽过，返回原结果)
  │                       │ 3. 读奖品池 remain ───▶│
  │                       │ 4. r1 = random()       │
  │                       │    r1 >= 0.25 ?        │
  │                       │ 5. 加权选等级 L        │
  │                       │ 6. 条件原子更新 ──────▶│ UPDATE ... WHERE remain>0
  │                       │ 7. 写中奖结果          │
  │◀──────────────────────┤                       │
  │  {level, name, time}  │                       │
```

**三个不可动摇的约束**

1. **抽奖判定 100% 在服务端**，客户端只负责展示动画，绝不接受客户端传回的中奖结果。
2. **库存扣减必须是条件原子更新**（`WHERE remain > 0`），禁止"先查后写"。
3. **唯一性由数据库唯一索引兜底**，应用层校验只是第一道防线。

## 5. 技术选型与实现策略

### 5.1 选型结论（推荐方案 A：微信云开发）

| 层级 | 选型 | 理由 |
| --- | --- | --- |
| 小程序框架 | **微信原生小程序 + Vant Weapp** | 单端交付、体积最小、组件齐全、无跨端适配成本 |
| 服务端 | **微信云开发 · 云函数（Node.js 18）** | 免备案、免服务器、免运维；内置登录态与数据库；自动扩缩容 |
| 数据库 | **云开发数据库（文档型）** | 支持原子操作 `_.inc(-1)` 与事务，满足库存扣减；配额足够 |
| 管理后台 | **Vue 3 + Vite + Element Plus** | 表格/导入导出组件成熟，静态托管即可 |
| Excel 处理 | 前端 `xlsx`（SheetJS）解析 + 服务端校验 | 导入在前端解析成 JSON 提交，服务端只做校验与写入，规避云函数解析大文件的性能问题 |
| 抽奖动画 | **lucky-canvas / @lucky-canvas/mini** | 开源、支持小程序、大转盘/九宫格开箱即用（详见对比报告） |
| 随机数 | `crypto.randomInt` / `crypto.randomBytes` | 可审计的公平随机，优于 `Math.random` |

**为什么推荐云开发**：内部活动场景下，云开发省掉了域名备案、HTTPS 证书、服务器运维三件最费时的事，从开发到上线可压缩到 3–5 个工作日。同类型项目（WeZhi 知识竞赛小程序）已验证该架构可承载题库导入 + 随机抽题 + 后台管理的完整闭环。

### 5.2 备选方案 B：自建服务（uni-app + Node/Express + MySQL 8）

| 对比项 | 方案 A（云开发） | 方案 B（自建） |
| --- | --- | --- |
| 上线周期 | **3–5 天** | 7–12 天 |
| 前置条件 | 小程序 AppID + 云环境 | 已备案域名 + HTTPS 证书 + 服务器 |
| 成本 | 按量，活动量级约几十元 | 服务器固定月费 |
| 抽奖一致性 | 条件原子更新 / 事务 | **事务 + 行锁，控制更精细** |
| 复杂查询 | 较弱（文档型） | 强（SQL 任意聚合） |
| 数据归属 | 腾讯云托管 | 完全自主 |
| 跨端扩展（H5/App） | 弱 | **强（uni-app 一套代码多端）** |

> **决策建议**：若活动为一次性/短期、无跨端需求 → **选 A**。若需沉淀为长期平台、要对接企业微信/H5、或企业对数据落地有硬性要求 → 选 B。

### 5.3 数据模型设计

```
activity（活动表）
├─ _id, name, status(draft|open|closed), start_at, end_at
├─ pass_score(3), question_count(5), win_rate(0.25), weight_mode
└─ created_at

question（题库表）  [索引: (activity_id, enabled)]
├─ _id, activity_id, no, title, options[A,B,C,D], answer, analysis
├─ enabled(bool), content_hash(去重)
└─ created_at

participant（参与者表）  【唯一索引: (activity_id, emp_no, name)】
├─ _id, activity_id, name, emp_no, openid
├─ passed(bool), passed_at, drawn(bool), drawn_at
└─ created_at

exam_record（答题记录，一人多条）
├─ _id, activity_id, participant_id, question_ids[], answers[]
├─ correct_count, passed, submitted_at
└─ ip, ua

prize（奖品池表）  【唯一索引: (activity_id, level)】
├─ _id, activity_id, level(1|2|3), name, total, remain, weight
└─ updated_at

lottery_record（中奖记录）  【唯一索引: (activity_id, emp_no, name)】
├─ _id, activity_id, participant_id, name, emp_no
├─ level(null=未中奖), prize_name, won_at
└─ client_ip

admin_log（操作日志）
└─ _id, admin_id, action, detail, created_at
```

**关键约束说明**

| 约束 | 作用 |
| --- | --- |
| `participant` 唯一索引 `(activity_id, emp_no, name)` | 保证一人一身份，防重复登记 |
| `lottery_record` 唯一索引 `(activity_id, emp_no, name)` | **数据库层兜底，物理上不可能重复中奖** |
| `prize.remain > 0` 条件更新 | 物理上不可能超发 |
| `exam_record` 与 `lottery_record` 分离 | 支持"答题多次、抽奖一次" |

### 5.5 安全与风控

| 风险 | 措施 |
| --- | --- |
| 抓包篡改中奖结果 | 抽奖结果 100% 服务端生成，客户端无写权限 |
| 刷题（枚举正确答案） | 抽题不下发答案；同一身份 10 次/分钟限流；异常作答明细可审计 |
| 接口重放/并发重复抽奖 | 唯一索引 + 幂等 token + 5s 幂等窗口 |
| 库存超发 | 条件原子更新（`WHERE remain > 0`） |
| 后台越权 | 管理员 RBAC、敏感操作二次确认、全量操作日志 |
| 数据泄露 | 姓名工号最小化展示、导出需审批留痕、活动后可一键脱敏 |

## 附录 A：核心抽奖算法伪代码

```js
const crypto = require('crypto');

function secureRandom() {
  return crypto.randomInt(0, 1e9) / 1e9; // [0,1)
}

async function drawLottery(activityId, participant) {
  // 1. 资格校验（应用层）
  if (!participant.passed) throw new BizError('未通关，暂无抽奖资格');
  if (participant.drawn)  throw new BizError('每人仅可参与一次抽奖');

  // 2. 唯一索引兜底：插入即占位（失败说明已抽过）
  const placed = await db.collection('lottery_record').add({
    data: { activityId, empNo: participant.empNo, name: participant.name,
            level: null, wonAt: null, createdAt: now() }
  }).catch(() => null);
  if (!placed) return queryMyResult(activityId, participant);

  // 3. 阶段一：中奖判定（恒定 25%）
  const { winRate } = await getActivityConfig(activityId);
  if (secureRandom() >= winRate) {
    return finalize(placed._id, { level: null, msg: '谢谢参与' });
  }

  // 4. 阶段二 + 三：选等级 + 原子扣减（最多重试 3 次）
  let pool = await loadPrizePool(activityId);           // remain > 0
  for (let attempt = 0; attempt < 3 && pool.length; attempt++) {
    const picked = weightedPick(pool, weightMode);      // A/B/C 策略
    const ok = await atomicDecrement(activityId, picked.level);
    if (ok) return finalize(placed._id, { level: picked.level, name: picked.name });
    pool = pool.filter(p => p.level !== picked.level);  // 被并发抢完，剔除后重试
  }

  // 5. 奖池为空或并发耗尽
  return finalize(placed._id, { level: null, msg: '谢谢参与' });
}

// 条件原子更新：remain > 0 才自减，返回是否成功
async function atomicDecrement(activityId, level) {
  const res = await db.collection('prize')
    .where({ activityId, level, remain: db.command.gt(0) })
    .update({ data: { remain: db.command.inc(-1), updatedAt: now() } });
  return res.stats.updated > 0;
}
```
