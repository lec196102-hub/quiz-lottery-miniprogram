# 答题抽奖小程序 — 测试功能方案

> 配套：原型 `prototype/index.html`、数据层 `prototype/test_data.js` / `prototype/data.js`、自动化验证 `prototype/verify_data.mjs`（27 断言）、`prototype/verify_lottery.mjs`（49 断言）。
> 前置需求文档：《PRD-答题抽奖小程序.md》。

## 1. 测试范围与策略

| 层级 | 手段 | 覆盖 |
|---|---|---|
| 单元 / 业务引擎 | Node 脚本断言（`verify_lottery.mjs` / `verify_data.mjs`） | 抽奖算法、库存扣减、防重复、题库导入、名单导出、字段一致性 |
| 界面走查 | 原型 `index.html` 手动点击 | PRD 8 条需求主路径 + 四态（空/加载/报错/成功） |
| 数据迁移 | 字段比对 | `test_data.js` → `data.js` 字段名/结构零改动 |

**策略原则**：抽奖引擎（唯一有资金风险的逻辑）以自动化为主、界面为辅；UI 以主路径 + 边界态走查为主。

## 3. 抽奖引擎专项自动化验证（`verify_lottery.mjs`，49 断言全绿）

执行：`node prototype/verify_lottery.mjs` → **结果：49 通过 / 0 失败**。

关键验证点：
- **TC-L1 随机抽取**：每轮从题库无放回抽 5 题，多次调用集合覆盖全题库。
- **TC-L2 通关阈值**：correct≥3 判定通关，边界值（2/3/4）严格。
- **TC-L3 中奖判定**：恒定 25% 中奖率，不随奖池余额变动（验证「抽完仍 25%」）。
- **TC-L4 加权选级**：在 `remain>0` 的等级间按剩余库存加权；一等自然稀缺。
- **TC-L5 库存原子扣减**：`UPDATE ... WHERE remain>0` 语义，并发模拟下 **oversold=0**。
- **TC-L6 防重复**：`lottery_record` 唯一索引 `(activityId, empNo)`，同一人工号物理不可二次写入。
- **TC-L7 奖池耗尽**：3000 次模拟后各等级剩余归零、总发出 = 155；耗尽后再抽 `won` 不增、无超发。
- **TC-L8 等级剔除**：抽完一等奖后继续模拟，一等发出 = 0、二/三等正常发满。
- **TC-L9 降级重试**：并发抢空时最多重试 3 次后降级，不抛异常。
- **TC-L10 后台**：错误密码被拒、正确登录成功且返回体不含密码、`listWinners` 与中奖人数一致、含时间字段、统计自洽、`CSV` 含表头。

**关键指标**（模拟 3000 次）：中奖率实测 ≈ 25.0%；发出分布受库存上限约束为一等 5 / 二等 50 / 三等 100。

> 注：按 PRD 设定，25% × 155 份 ≈ 需 **620 人次**抽奖送完。若实际参与人数远低于此，活动结束将剩余奖品——参见 §7 待决策 Q3。

## 4. 数据层字段一致性验证（`verify_data.mjs`，27 断言全绿）

执行：`node prototype/verify_data.mjs` → **结果：27 通过 / 0 失败**。

要点：`test_data.js` 导出字段与 PRD §5.3 数据模型完全一致（未重命名/裁剪）；`data.js` 仅做 `import` 与引用封装；答题记录工号均存在于参与者表；`correctCount` 与 passed 一致；管理员账号存在。

## 5. 边界与异常用例

| 用例 | 场景 | 预期 |
|---|---|---|
| TC-B01 | 题库不足 150 题导入 | 导入校验报错，阻断 |
| TC-B02 | 导入含重复题干 | 自动忽略重复，计数真实新增 |
| TC-B03 | 网络抖动加载题库 | quiz 页 Toast 重试，不丢进度 |
| TC-B04 | 并发同时抽最后一奖品 | 仅一人成功，其余降级/未中，零超发 |
| TC-B05 | 活动已结束进 home | 报错态提示「活动已结束」 |
| TC-B06 | 奖品全抽完进 lottery | 提示「奖品已全部送出」，入口关闭 |

## 6. 兼容性

- 原型为单文件 HTML（ES Module），需经 HTTP 提供（`python -m http.server` 或任意静态服务）；`file://` 直接打开会因模块跨域受限。
- 目标运行环境：微信小程序基础库（正式接入时按 PRD 技术栈替换 `data.js` 为云函数/请求）。

## 7. 已知风险与待决策项（PRD §10）

| 项 | 内容 | 影响测试 |
|---|---|---|
| Q1 | 中奖后等级分配策略（建议按剩余库存加权） | 决定 TC-L4 加权方式 |
| Q2 | 奖品全抽完处理（建议关闭入口） | 决定 TC-B06 文案与守卫 |
| Q3 | 预计参与人数 | 决定中奖率 25% 是否需调整（影响送完所需人次） |
| Q4 | 技术选型（建议微信云开发） | 决定 `data.js` 替换为云函数的改造量 |

## 8. 回归与持续集成建议

- 将 `verify_data.mjs` 与 `verify_lottery.mjs` 纳入提交前钩子（pre-commit），任意数据/算法改动触发全量 76 断言。
- 原型主路径（TC-F01~F12）每次迭代手工走查一次，记录四态截图。
- 接入真实后端后，新增接口契约测试：唯一索引防重、库存 `WHERE remain>0` 原子性、登录不返回密码。

---
**结论**：数据层（27）+ 抽奖引擎（49）共 76 条自动化断言全绿，原型覆盖 PRD 八条需求主路径与四态。当前唯一需业务方拍板的是 §7 的 Q1–Q4，其中 Q3（参与人数）直接决定 25% 中奖率能否在活动期内送完奖品。
